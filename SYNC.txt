# GUI Sync Plan — keep `sectorforge-gui` and `sectorforge-builder` visually identical

## Problem
Two binaries (`gui` viewer/editor, `builder`) both render the sector map. Today:
- `gui-core/src/sector_view.rs` (1166 lines) is the shared widget.
- `gui/src/app/sector_view.rs` (688 lines) wraps and re-implements some paint logic.
- `builder/src/builder/panels/map.rs` (765 lines) does the same in the builder.

Any new map element (route style, glyph, faction color, region overlay) risks landing in only one of the three. The goal is structural — make it *impossible* for the two apps to diverge, not just "remember to update both."

## Strategy — layered shared-render pattern

### 1. Single `MapRenderer` in `gui-core`, pure function over `&Painter` + data
Move every pixel-producing line into one entrypoint:
```rust
pub fn paint_sector(painter: &Painter, view: &MapView, model: &SectorModel, theme: &MapTheme);
```
- No widget state, no interaction logic inside.
- Both apps call this exact function.
- Builder paints *on top* (selection, ghosts, hover) via separate `paint_overlay_*` functions in `gui-core` — never re-draws what `paint_sector` owns.

### 2. `MapTheme` struct = one source of truth for visuals
- Colors, hex radius, stroke widths, font size, glyph table, z-order constants.
- No magic numbers in `gui/` or `builder/` crates.
- `MapTheme` is deserializable (TOML via existing `toml` dep) so designers can tweak without recompile.

### 3. Split render from interaction
- `gui-core` owns: geometry (`hex_to_screen`, `screen_to_hex`), painting, hit-testing.
- Apps own: input handling, selection model, tool state.
- Hit-test logic stays in core so click→hex math cannot disagree between apps.

### 4. Embed as a `Widget`, not via copy-paste
Target API:
```rust
gui_core::MapView::new(&model, &theme)
    .with_selection(&sel)
    .with_overlay(|p, ctx| builder_ghosts(p, ctx))
    .show(ui)
```
Builder and viewer differ only in callbacks + surrounding chrome. The hex/route/glyph/label paint code is identical because it is literally the same function call.

### 5. Snapshot tests in `gui-core` — the "at all times" guarantee
This is the enforcement layer; without it the shared code will still rot.
- Use `egui_kittest` (official egui snapshot harness) — preferred.
- Fallback: render `Painter` shapes to an image buffer via the `image` crate, hash with `blake3`, compare against a committed golden.
- Golden images per element: hex tile, route segment, system glyph variants, region overlay, label.
- Plus one full small fixture sector covering all element types.
- CI fails on drift. Golden updates are explicit and reviewable.

### 6. Visual token enums, not strings or ad-hoc constants
```rust
pub enum FactionGlyph { Imperium, Chaos, Xenos(XenosKind), /* ... */ }
impl FactionGlyph {
    pub fn paint(self, p: &Painter, at: Pos2, theme: &MapTheme);
}
```
- Add a variant in one place → both apps render it.
- Compiler enforces exhaustiveness via `match`.

### 7. Forbid `egui::Painter` use outside `gui-core`
Architectural wall:
- Add a clippy `disallowed_types` lint in `gui/` and `builder/` Cargo configs / `clippy.toml` entries.
- `egui::Painter` is disallowed in those crates.
- Map paint code *cannot compile* outside `gui-core`. Hard guarantee, not a convention.

## Why this beats "just remember to update both"
- Steps 1–4 give a *substrate* — shared widget, shared theme, shared tokens.
- Steps 5–6 give a *ratchet* — lint wall + snapshot tests catch drift in CI, not at review time.
- Templates alone (e.g., a written checklist) decay. The compiler + golden tests do not.

## Resolved decisions
- Snapshot tests use the documented fallback path: headless `egui::Context` + `image` rasterization + `blake3` goldens.
- `MapTheme` ships as a hardcoded default today; optional TOML override remains a future extension.
- Builder/editor overlays stay as shared `SectorView` inputs and `gui-core` paint helpers until a dedicated overlay trait becomes necessary.
