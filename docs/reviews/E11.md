## 0. TL;DR decision (already made — don't relitigate unless asked)

The review's literal fix — **table-drive the menus behind a `MenuItem { label,
action, enabled }` struct so `SectorMenuAction` is the single source of truth** —
was assessed and judged **not worth the churn**:

- The action ⇄ label ⇄ effect mapping is **already centralised** in
  `sector_menu_action_label` (label) + `apply_sector_menu_action` (dispatch). The
  `render_*` functions own menu *composition* (which actions appear in which menu,
  enabled-state, ordering, grouping, submenu nesting, confirm flows, dynamic
  current-markers) — that is genuine per-menu UX, **not** duplicated boilerplate.
  Table-driving does not make `SectorMenuAction` "more" the SSOT than it is.
- The menu items span **10+ heterogeneous shapes** (enumerated in §3). A
  `MenuItem` rich enough to model them all degrades into a deeply-nested variant
  DSL whose render loop is ~as complex as today's imperative code, with *more*
  indirection.
- The `render_*` builders have **no headless test net** (they need a live egui
  interaction loop). A behaviour-restructure there is un-netted risk. (NB: the
  *dispatch/resolve* core **is** netted — see §2 — but the builders are not.)

**Recommended resolution: Option A — a verbatim dir-module split** (§4). It
addresses the real half of the finding ("the 1162-LOC file is itself a
god-file") at **zero behaviour risk** (a verbatim move cannot change behaviour),
using the exact playbook E7/E4/E10/F3/F8 already used in this review. The
risky/marginal table-drive is declined and documented.

If the owner still wants the table-drive, **Option B** (§5) documents how to do it
as safely as possible, including the DSL that is *actually* required and a manual
verification protocol — but lead with Option A unless told otherwise.

## 2. The test net (important — it de-risks Option A and bounds Option B)

`map/mod.rs`'s `#[cfg(test)] mod tests` unit-tests the **pure** half:

- `resolve_sector_context` — hit-testing on a synthesised `SectorGeom`.
- `apply_sector_menu_action` — round-trips for ~all variants (place/paint/erase,
  focus/rename/delete, add-route/add-world, regenerate/pin, multi-*, route
  type/stability, region recolor/rename, cancel-route, partial-regen, …).
- `sector_menu_action_label` — `action_labels_match`.
- `should_dismiss_sector_context_menu`, `sector_menu_target_is_stale`.

**Consequence for Option A:** the *netted* code (`resolve_sector_context`,
`SectorMenuAction`/`OpenInTarget`, `sector_menu_action_label`,
`apply_sector_menu_action`, the two predicates, `menu_anchor_pivot`) moves
**byte-for-byte**, and the same tests keep exercising it through the preserved
re-exports. The split therefore has a live regression net on everything except
the interactive `render_*` builders — and those move verbatim too (a verbatim
move cannot change behaviour). This is why Option A is safe.

**Consequence for Option B:** if you restructure the builders, the net does
*not* cover them. Before touching a builder you must either add headless coverage
or run the interactive smoke in §5.4.

## 3. The 10+ menu-item shapes (why the table-drive is the hard/risky path)

Catalogued from the five builders. A faithful `MenuItem` must model **all** of
these or it will silently drop behaviour:

1. **Always-enabled action** — `if ui.selectable_label(false, "X").clicked() {
   close |= apply(state, ACTION); }` (FOCUS, RENAME, DELETE, ADD ROUTE, …).
2. **Enabled-with-disabled-hover** — `add_enabled(cond, SelectableLabel::new(false,
   "X"))` + `if !cond { resp.on_hover_text("why disabled") }` (PAINT/ERASE REGION,
   REGENERATE SYSTEM, WORLD open-in, PIN/UNPIN ALL, RESEED WORLDS).
3. **`on_disabled_hover_text`** (a *different* egui API) — the no-factions
   `ASSIGN PRIMARY FACTION ▸` disabled `menu_button`.
4. **Dynamic label from state** — `pin_label = if pinned { "UNPIN" } else
   { "TOGGLE PIN" }`.
5. **Dynamic current-marker label** — `• {label}` when `value == current`
   (CYCLE ROUTE TYPE, CYCLE STABILITY, RECOLOR, FLIP CONTROL STATE).
6. **Clipboard items that bypass the action enum** — COPY ID / COPY COORD do
   `ui.output_mut(|o| o.copied_text = …); close = true;` — **no**
   `SectorMenuAction`.
7. **Nested submenus** — `ui.menu_button("… ▸", |ui| { … ui.close_menu() })`
   (ASSIGN PRIMARY FACTION with a *dynamic* faction list, FLIP CONTROL STATE,
   CYCLE ROUTE TYPE, CYCLE STABILITY, RECOLOR).
8. **Inline two-step confirm flow** — multi-select `DELETE ALL` toggles
   `state.sector_context_menu.bulk_delete_confirm` and renders Yes/No buttons; the
   "No" path mutates transient menu state directly (no action).
9. **Italic header labels** — route/region summary lines
   (`ROUTE {id} — {type} / {stability}`, `REGION {id} — {name} [{kind}]`).
10. **CLOSE-on-stale fallback** — route/region builders early-return a lone
    `CLOSE` item when the target id is no longer in the sector.
11. **Mode-gated collapse** — `render_system_menu` early-returns a 2-item menu
    (`CANCEL ROUTE` + `Open in ROUTES`) while `state.pending_route_start.is_some()`.
12. **Plain count label** — `ui.label(format!("{} systems selected", n))`.
13. **Separators** between groups.

A `MenuItem` enum that captures all of this is roughly:
`Action{label,action,enabled,disabled_hover}` | `Clipboard{label,text}` |
`Separator` | `Header(String)` | `ConfirmFlow{…}` | `SubMenu{label, enabled,
disabled_hover, items}` | `DynamicMarker{…}`. That is a DSL, not a table.

## 4. OPTION A (recommended): verbatim `map/context_menu/` dir-module split

Mirror of E7 (`system/`), E4 (`world/`), E10 (`control/`), F3, F8. **No logic
changes** — slices taken at item boundaries; bodies byte-identical except for
mechanical path/visibility edits, proved by diff.

### 4.1 Target layout

```
map/context_menu/
  mod.rs      — module doc, shared imports, `mod` decls, the pub-API re-exports,
                and `show_sector_context_menu` (the entry that dispatches to a
                builder). ~70–100 LOC.
  resolve.rs  — resolve_sector_context, should_dismiss_sector_context_menu,
                sector_menu_target_is_stale, menu_anchor_pivot. (Pure, netted.)
                ~210 LOC.
  action.rs   — enum SectorMenuAction, enum OpenInTarget, sector_menu_action_label,
                apply_sector_menu_action. (The netted dispatch core.) ~470 LOC.
  render.rs   — the five render_* builders + stability_label. (Interactive,
                un-netted; verbatim.) ~510 LOC.
```

Rationale for these seams: it separates the **netted pure logic** (resolve +
action) from the **un-netted interactive builders** (render), which is the most
useful boundary for future work and keeps each file well under ~500 LOC.
`show_sector_context_menu` stays in `mod.rs` because it is the glue that wires
`resolve`/predicate gating → a `render::*` builder → `menu_anchor_pivot`; keeping
it in `mod.rs` lets it call the `render::*` builders and the `resolve::*` helpers
without extra re-exports.

### 4.2 Visibility plan (the fiddly part — read carefully)

After nesting one level deeper, items that `map/` consumes must be re-exported
from `mod.rs` at **map-visibility**. The E7 gotcha applies: **`pub(super) use` of
a `pub(super)` item trips E0364** (you'd be widening visibility). Avoid it by
giving the cross-boundary items an **explicit path visibility** equal to what the
external consumers need, then re-exporting (a *narrowing* or equal re-export is
always legal):

- In `action.rs` / `resolve.rs`, declare the items that `map/` consumes as
  **`pub(in crate::builder::panels::map)`** (this is exactly the visibility
  `menu_anchor_pivot` already uses — match it):
  `resolve_sector_context`, `SectorMenuAction`, `OpenInTarget`,
  `sector_menu_action_label`, `apply_sector_menu_action`,
  `should_dismiss_sector_context_menu`, `sector_menu_target_is_stale`,
  `menu_anchor_pivot`.
- In `mod.rs`, re-export them so the surface stays at `context_menu::`:
  ```rust
  mod action;
  mod render;
  mod resolve;

  pub(super) use action::{
      apply_sector_menu_action, sector_menu_action_label, OpenInTarget, SectorMenuAction,
  };
  pub(super) use resolve::{
      menu_anchor_pivot, resolve_sector_context, sector_menu_target_is_stale,
      should_dismiss_sector_context_menu,
  };
  ```
  (`pub(super)` here = visible to `map`. Re-exporting `pub(in …::map)` items as
  `pub(super)` from a module *inside* `map` is an equal-visibility re-export →
  legal. Confirm with `cargo check`, not rust-analyzer.)
- The **five `render_*` builders + `stability_label`** are called only by
  `show_sector_context_menu` (in `mod.rs`), so mark them **`pub(super)`** in
  `render.rs` (= visible to `context_menu`/`mod.rs`). They are **not** re-exported.
- `show_sector_context_menu` stays `pub(super)` in `mod.rs` (already map-visible).
- Cross-submodule *internal* calls: `apply_sector_menu_action` (action.rs) is
  called by the `render_*` builders (render.rs) → reachable via
  `use super::action::apply_sector_menu_action;` in render.rs (or via the
  `super::` re-export). `sector_menu_action_label` is called inside
  `apply_sector_menu_action` (same file — fine). `paint_region_at`
  (`super::interactions`) is used by `apply_sector_menu_action` → in action.rs use
  `crate::builder::panels::map::interactions::paint_region_at` or
  `super::super::interactions::paint_region_at`.

> If `cargo check` reports an E0364 or a private-in-public error, **trust it**
> and bump the named item to `pub(in crate::builder::panels::map)`. Ignore
> rust-analyzer E0599/E0432 flurries on freshly-split modules — they are stale;
> `cargo check -p sectorforge-builder` is the oracle.

### 4.3 Import bookkeeping

Each submodule gets only the imports its moved bodies use; `cargo fix --lib -p
sectorforge-builder` (or clippy's unused-import suggestions) will trim leftovers —
but **re-diff bodies afterwards** to confirm `fix` touched only `use` lines.
Likely placement:

- `resolve.rs`: `egui::Pos2`, `SectorGeom`, `state::SectorMenuTarget`,

- `action.rs`: ids, `sector_model::{…}`, `command::BuilderCommand`, the

- `mod.rs`: `egui`, `BuilderState`, the `mod`/`use` glue, and whatever

## 5. OPTION B (only if owner explicitly chooses the table-drive)

Higher risk; do **not** start without owner sign-off and the verification
protocol in §5.4. Lead with Option A.

### 5.1 The DSL you actually need

```rust
enum MenuItem {
    Action { label: String, action: SectorMenuAction, enabled: bool,
             disabled_hover: Option<&'static str> },
    Clipboard { label: String, text: String },     // COPY ID / COPY COORD
    SubMenu  { label: String, enabled: bool, disabled_hover: Option<&'static str>,
               items: Vec<MenuItem> },              // the ▸ menu_buttons
    Header(String),                                 // italic summary lines
    Note(String),                                   // "N systems selected"
    Separator,
}
```
The two-step `DELETE ALL` confirm flow (shape 8) and the mode-gated system-menu
collapse (shape 11) do **not** fit the table — keep them as bespoke imperative
code outside the generic renderer, or model them with extra variants
(`ConfirmFlow`, and an early `if` before building the Vec). Don't force them.

### 5.2 Build + render split

Per menu, a `fn build_*_items(state, …) -> Vec<MenuItem>` (pure, **testable** —
this is the upside: you can finally unit-test menu composition) and a single
generic `fn render_items(ui, state, &[MenuItem]) -> bool` that walks the Vec.
Dynamic current-markers (shape 5) must be baked into `label` at build time.

### 5.3 Per-menu risk notes

- `render_multi_selection_menu` is the worst: the confirm flow + two `menu_button`
  submenus (one with a dynamic faction list) + `on_disabled_hover_text`. Convert
  last, or leave bespoke.
- `render_system_menu`: the `pending_route_start` early-collapse must remain a
  guard *before* the Vec is built.
- `render_route_menu` / `render_region_hex_menu`: the CLOSE-on-stale early return
  must remain; the ▸ submenus carry `•` current-markers.
- Clipboard items must keep using `ui.output_mut(|o| o.copied_text = …)` and set
  `close = true` — they are **not** `SectorMenuAction`s.

### 5.4 Verification protocol (mandatory for Option B)

There is **no snapshot/headless net for the builders**. So:
1. First, *add* headless coverage for the new `build_*_items` functions (assert
   the item list — labels, enabled flags, actions — for representative states:
   empty hex with/without a selected region, system pinned/unpinned/has-world,
   multi-select all-pinned/mixed, route/region present/stale). This converts the
   un-netted risk into a netted one and is the main reason the DSL is even worth
   it.
2. `cargo test -p sectorforge-builder --lib` green (≥319 + the new tests).
3. `cargo clippy --workspace --all-targets -- -D warnings` clean.
4. **Interactive smoke** (no automated substitute): `cargo run -p
   sectorforge-builder` (or the `sbuild` quick-profile alias) → MAP tab →
   right-click an empty hex, a system (pinned & unpinned), a multi-selection, a
   route, a region hex; exercise every item incl. the DELETE-ALL confirm, the ▸
   submenus, COPY ID/COORD (check clipboard), and a stale target. Confirm
   enabled/disabled + hovers match `main`.

### 5.5 Fallback

If full conversion proves too risky, the instruction's escape hatch is "**convert
only the clean menus and note the rest**." There is **no fully-clean menu** (every
builder has an enabled-predicate, a submenu, a clipboard item, or a confirm
flow), so "clean" here means at most the simple always-enabled items within a
menu — marginal. Prefer Option A over a half-converted Option B.

## 6. Hard rules carried forward (apply to either option)

- **§R4 command bus.** Document-state mutations go through `BuilderCommand` (or
  the `edit_world`/`edit_system` wrappers). In this file the document edits are
  already inside `apply_sector_menu_action`; the `render_*` builders only mutate
  **transient** UI state (`state.sector_context_menu.bulk_delete_confirm`,
  pending-* dialogs) directly — that is the documented transient-UI carve-out, not
  a bus violation. **Preserve this**: a verbatim split keeps it as-is; Option B
  must not move a document mutation out of `apply_*`.
- **Gate per commit:** `cargo clippy --workspace --all-targets -- -D warnings`
  clean **+** `cargo test -p sectorforge-builder --lib` green (≥319). Golden /
  map-snapshots **not** run (builder-only; no `sectorforge`/`gui-core` source, no
  render-path change).
- **Trust `cargo check`/`clippy`, not rust-analyzer** squiggles — split modules
  throw stale E0599/E0432/"not in any crate" flurries that compile fine.
- **No `cargo fmt --all`** (repo isn't rustfmt-clean — reformats ~20 unrelated
  files). Keep only your added lines fmt-correct.
- **No `cd <project> &&`** prefix in Bash (cwd persists at repo root).
- **Delegate the bulk carve** (rust-explorer → one panel-implementer applier),
  then **re-verify in the main thread** yourself (byte-diff + gate). Keep the
  reviewable change in the main thread.
- **Commit directly on `main`** (no branch, no PR), and **push**. Trailer:
  `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.
- **Update `docs/reviews/PROGRESS.md`** (dated log + roll-up + AREA-E §En status),
  `docs/reviews/AREA_E_builder_panels.md` (E11 status), and — since files move —
  `docs/MAP.md`; non-trivial structure changes → `GUIDE.md`.
