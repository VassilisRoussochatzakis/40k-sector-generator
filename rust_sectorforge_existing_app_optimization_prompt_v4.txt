1. NON-NEGOTIABLE REVIEW RULES
--------------------------------------------------------------------------------

Follow these rules strictly:

1. Work with the existing Rust architecture.
   - Preserve the Rust-only constraint.
   - Preserve the existing library + binary + gui workspace shape unless there is strong evidence that a crate-boundary adjustment is needed.
   - Prefer optimizing the current sectorforge core and GUI integration instead of proposing a rewrite.

2. Evidence first.
   - Clearly separate measured facts, Cargo.toml facts, code observations, user-reported symptoms, reasonable inferences, and assumptions.
   - Do not invent benchmark numbers, data sizes, frame rates, memory usage, UI framework details, or generation behavior.
   - If gui/Cargo.toml is missing, say that GUI-specific dependency conclusions are incomplete.

3. Determinism and correctness are performance requirements.
   - For a generator-style application, fast output is not acceptable if it changes results unexpectedly.
   - Preserve seeded reproducibility, stable output formats, stable hashing/fingerprinting, stable paths, deterministic ordering, and round-trip behavior.
   - Treat nondeterministic outputs, stale GUI views, incorrect rendered/generated points, wrong PNG output, wrong save/export content, or inconsistent hashes as correctness and performance defects.

4. Profile before optimizing.
   - Use profiling, tracing, Criterion benchmarks, and targeted instrumentation to identify bottlenecks.
   - Do not recommend speculative micro-optimizations unless they are low risk and likely high value.
   - Every significant optimization should include a before/after measurement plan.

5. Preserve user-visible behavior.
   - Avoid changes that alter generation semantics, RNG sequences, serialized config shape, output file naming, output ordering, hash values, image dimensions, image contents, or CLI behavior unless those changes are intentional and covered by tests.

6. Keep the GUI responsive.
   - Expensive generation, image export, config loading, validation, hashing, or file I/O should not block the GUI event loop.
   - Use message passing, snapshots, cancellation, progress reporting, and stale-result rejection where appropriate.
   - All UI mutations must remain on the appropriate GUI thread for the chosen GUI framework.

7. Avoid overengineering.
   - Do not introduce async runtimes, databases, ECS frameworks, large data-processing frameworks, or complex worker systems unless the code evidence and workload justify them.
   - Prefer small, idiomatic Rust changes first: data layout improvements, fewer clones, better borrowing, preallocation, chunking, cache invalidation, targeted recomputation, and clearer crate boundaries.

3. CODE AREAS TO REVIEW FIRST

Review the code in this order unless repository evidence suggests a better path:

A. Crate boundaries and public API
- src/lib.rs should contain reusable, testable core logic.
- src/main.rs should be a thin CLI wrapper around sectorforge where practical.
- gui should call the sectorforge library through stable APIs rather than duplicating generation logic.
- Shared behavior between CLI and GUI should live in the library, not in UI-specific code.
- Avoid leaking GUI-specific types into the core model unless there is a deliberate adapter layer.

Questions:
- Are CLI and GUI using the same generation code path?
- Is the core library deterministic and independent from UI state?
- Are public APIs ergonomic enough to avoid unnecessary clones by callers?
- Are error types useful for both CLI messages and GUI diagnostics?

B. Generation pipeline
Because the project has rand, rand_chacha, blake3, Criterion, and a generation benchmark, inspect generation performance and determinism carefully.

Review:
- Seed handling and RNG initialization.
- Whether deterministic paths use ChaCha consistently rather than thread_rng or nondeterministic entropy.
- Whether RNG state is passed explicitly and predictably.
- Whether generation order depends on HashMap iteration, thread scheduling, filesystem ordering, or other nondeterministic sources.
- Hot loops, allocation patterns, clone frequency, string creation, temporary Vecs, and repeated recomputation.
- Whether generated entities have stable typed IDs.
- Whether intermediate data structures are kept longer than needed.
- Whether generation can be incrementally recomputed when GUI settings change.

Questions:
- For the same config and seed, does generation produce identical semantic output across repeated runs?
- If byte-identical output matters, is serialized ordering stable too?
- Is generation CPU-bound, allocation-bound, hash-bound, image-bound, or I/O-bound?

4. RUST-SPECIFIC OPTIMIZATION CHECKLIST
--------------------------------------------------------------------------------

Use this checklist when reviewing code. Recommend only changes supported by evidence.

A. Allocation and clone reduction
Look for:
- Cloning Vec, String, PathBuf, images, generated entities, or full model structs in hot paths.
- collect::<Vec<_>>() where iterators could be consumed directly.
- Repeated String formatting in loops.
- Repeated serialization/deserialization as a cloning mechanism.
- Temporary maps/sets rebuilt on every GUI frame.
- Per-frame regeneration or per-frame image buffer rebuild.

Consider:
- Borrowing slices: &[T], &str, &Utf8Path.
- Returning iterators where ergonomic.
- Using Cow only when it meaningfully reduces copies.
- Preallocating Vec/String/ImageBuffer with known capacity.
- Reusing scratch buffers where ownership is clear.
- Keeping owned outputs only at API boundaries where needed.

B. Data structures
Look for:
- HashMap/BTreeMap choice and deterministic-order requirements.
- Vec scans in hot paths that need indexes.
- String keys where typed IDs or compact integer IDs would be better.
- Dense generated entities stored in pointer-heavy structures.
- Rc/Arc where plain ownership or borrowing would suffice.

Consider:
- Vec for dense ordered storage.
- BTreeMap or sorted Vec when deterministic iteration matters.
- HashMap when lookup speed matters and output ordering is not derived from map iteration.
- Typed newtype IDs for entity identity.
- Index arrays for GUI-visible order/filtering.
- Separate internal model structs from serialized DTOs if needed.

C. Ownership and shared state
Look for:
- Rc/RefCell or Arc<Mutex<_>> used to bypass design issues.
- Locks in render paths.
- Long-held locks around generation or I/O.
- Shared mutable state between GUI and worker threads.
- Background tasks mutating the same model the GUI is reading.

Consider:
- Immutable snapshots.
- Message passing.
- Short-lived locks with clearly documented ownership.
- Arc for sharing immutable models.
- Revision IDs for snapshot freshness.
- Single-writer model updates through explicit transactions.

D. Iterators and hot loops
Look for:
- Excessive iterator chains in extremely hot loops where profiling shows overhead.
- Unnecessary bounds checks or coordinate conversions in per-pixel loops.
- Repeated validation of values already known valid.
- Branch-heavy code in tight generation loops.

Consider:
- Clear loops when they are faster and easier to profile.
- Hoisting invariant calculations.
- Precomputing lookup tables if they are stable and bounded.
- Avoiding unsafe unless profiling proves a need and tests protect correctness.

E. Parallelism and background work
Do not recommend parallelism automatically. First determine whether the bottleneck is CPU-bound and whether generation is deterministic under parallel execution.

If parallelism is justified, require:
- Deterministic output ordering.
- Deterministic RNG partitioning or per-task seeded RNG streams.
- No shared mutable output without synchronization.
- Stable merge order.
- Benchmarks proving benefit.
- GUI responsiveness improvement, not just total throughput improvement.

Possible approaches after evidence:
- std::thread for simple worker jobs.
- scoped threads if suitable.
- rayon only if adding a dependency is justified and deterministic merging is handled.
- channels for GUI worker communication.
- Cancellation flags or generation IDs for long-running work.

F. Build profiles
The release profile is already aggressive: fat LTO, one codegen unit, panic abort, strip symbols.

Review:
- Whether developer builds are slow because release settings are overused in normal iteration.
- Whether bench profile with thin LTO is appropriate for repeatable benchmarks.
- Whether profile settings hide useful symbols during profiling.
- Whether panic = abort is acceptable for release crash behavior.
- Whether debug info should be enabled in a profiling profile.

Recommendations:
- Do not present LTO/codegen-units as missing; they already exist.
- Consider adding a separate profiling profile if symbolized flamegraphs are needed.
- Keep benchmark profile stable and documented.
- Compare performance using the same profile consistently.

8. HIGH-VALUE FINDINGS TO LOOK FOR IN THIS PROJECT
--------------------------------------------------------------------------------

Look specifically for these patterns:

Generation performance anti-patterns:
- Rebuilding the entire generated model after every small GUI setting change when incremental recomputation is possible.
- Using nondeterministic RNG or map iteration in output-affecting paths.
- Repeated allocation of temporary Vecs, Strings, maps, or image buffers.
- Cloning the full generated model for CLI, GUI, export, and render cache without need.
- Hashing or serializing large structures repeatedly inside loops.
- Debug formatting used as a canonical representation.

GUI anti-patterns:
- Running generation, hashing, PNG encoding, or file I/O on the GUI thread.
- Regenerating on every frame rather than on input changes.
- Holding locks while rendering.
- Updating GUI state directly from worker threads.
- Applying stale worker results after settings/seed/config changed.
- Selection/hover/edit state tied to visible index rather than stable entity ID.
- Recreating preview textures/images unnecessarily.

Serialization/path anti-patterns:
- Using serialized JSON/TOML strings as internal data transfer between modules.
- Panicking on malformed configs.
- Missing config version/default handling.
- Hashing noncanonical serialized output when field/map order can change.
- Converting paths through lossy strings unnecessarily instead of using camino types where appropriate.

Image/output anti-patterns:
- Allocating a new image buffer for every minor preview update without need.
- Encoding PNG just to display a GUI preview.
- Performing expensive per-pixel calculations that can be precomputed.
- Building a full intermediate image and then copying it into another full buffer.
- Comparing PNG bytes in tests when metadata/compression variation makes pixel comparison more appropriate, unless byte-identical PNGs are required.

Testing/benchmarking anti-patterns:
- Criterion benchmark covers only a toy case.
- Benchmark includes random setup that changes every run.
- No fixed-seed benchmark inputs.
- No golden outputs for deterministic generation.
- No test proving CLI and GUI use equivalent generation paths.
- No test preventing stale GUI worker results.
- No regression threshold in CI for generation benchmark.
