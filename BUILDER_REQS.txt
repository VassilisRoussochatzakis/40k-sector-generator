# BUILDER_REQS.txt
# Requirements: Full GUI Sector Builder (1:1 parity with sectorforge CLI/generator)
# Target crate moved 2026-05-24 from sectorforge-gui to sectorforge-builder.
# References to gui/src/builder/ in older revisions now point to
# builder/src/builder/.
# Target app/crate: sectorforge-builder (builder/src/)
# Viewer/editor app/crate: sectorforge-gui (gui/src/) -- no builder panels live here.
# Shared egui utility crate: sectorforge-gui-core (gui-core/src/).
# Backing crate: sectorforge (src/)
# Handoff contract: builder writes a project directory; viewer opens the same
# project via `sectorforge-gui --project <dir>` / `cargo sgui --project <dir>`.
# No in-process builder embedding in sectorforge-gui, no IPC, no shared memory.
# Goal: user constructs an arbitrary sector from scratch, system-by-system,
#       through the dedicated builder GUI alone, with access to every
#       CLI/library feature that affects sector data, derived overlays,
#       validation, or export.

================================================================================
0. SCOPE
================================================================================

The builder must let a user:
  * Start from a blank `GeneratedSector` (no CLI invocation required).
  * Place / move / delete every entity (system, world, route, region, faction,
    presence, claim, control state, orbital asset, surface region, archetype,
    conflict state, intel record, history event, mission, site, persona).
  * Configure every input file (sectorforge.toml, factions.toml,
    relations.toml, route_rules.toml, regions.toml, economy.toml, history.toml,
    system_names.toml, world_names.toml, wishes.toml, map_theme.toml,
    segmentum.toml, worlds.toml).
  * Invoke every derivation pipeline (search, history, personae, hooks,
    relations, regions, economy, prose, missions, sites, briefing,
    interestingness, analyze, diff, compose) without leaving the builder app.
  * Validate (pre + post invariants) and see errors anchored to the
    offending entity in the model.
  * Export every artifact (JSON, Markdown, sector PNG, per-system PNG,
    self-contained HTML, manifest, super-manifest).
  * Re-roll seeds, lock seeds, snapshot/revert via the in-memory history
    layer, all without losing manual edits in unaffected entities.

This document is a checklist. Each item is a separate, testable unit. The
ordering inside a section is roughly dependency-first.

================================================================================
0.1. APP BOUNDARY CONTRACT
================================================================================

B0.   `sectorforge-builder` is the only target app for this checklist. All new
      builder panels, modals, workspace state, command routing, project I/O,
      and builder-specific tests belong under `builder/src/`.

B1.   `sectorforge-gui` remains the viewer/editor for generated sectors. It may
      keep legacy viewer/editor affordances (sector load, direct sector edit,
      data editor, export UI), but it must not regain `BuilderState`,
      `BuilderWorkspace`, `BuilderCommand`, or `builder/src/builder/panels/*`.

B2.   `sectorforge-gui-core` is the only shared GUI crate. Put reusable,
      app-neutral egui helpers here (jobs, palette, read-only sector/system
      widgets, info formatting, heatmap wrappers). Do not make `gui-core`
      depend on `sectorforge-gui` or `sectorforge-builder`.

B3.   Builder -> viewer integration is file-based. `sectorforge-builder` saves
      `sectorforge.toml`, referenced catalogs, `<outputs.directory>/sector.json`,
      and manifest data. `sectorforge-gui --project <dir>` loads/reloads those
      files through its normal project path. Any "open in viewer" affordance
      should spawn `sectorforge-gui --project <dir>` as an external process.

B4.   Canonical launch commands:
        Builder: `cargo sbuild --project <dir>`
        Builder help: `cargo run -p sectorforge-builder -- --help`
        Viewer/editor: `cargo sgui --project <dir>`
      Tests and smoke docs should name the app being launched.

1. RUST ARCHITECTURE PRINCIPLES
================================================================================

R1.   [DONE] Single source of truth = `GeneratedSector` from
      `src/sector_model.rs`. `BuilderState` owns the sole live sector by
      direct ownership behind `&mut BuilderState` — equivalent to the
      `Rc<RefCell<>>` option in the spec (GUI thread is sole writer; jobs
      hold cloned read-only snapshots). Design choice documented in
      `builder/src/builder/state.rs`.

R2.   [DONE] All `BuilderCommand`, `BuilderIndex`, `BuilderState`, and
      `SessionFile` ID fields are the typed `SystemId` / `WorldId` /
      `RouteId` / `FactionId` from `src/ids.rs`. Free strings in these
      modules are only error messages, display names, base64 file payloads,
      or cache keys.

R3.   [DONE] `builder/src/builder/index.rs::BuilderIndex` keys every map with
      `BTreeMap<TypedId, usize>` (or `(usize, usize)` for worlds). Rebuilt
      after every mutation by the command bus.

R4.   [DONE] `BuilderState::run` enforces all four rails:
      (a) invariant re-check via `sectorforge::invariants::check_sector`
      stored in `invariant_report`,
      (b) snapshot/undo stack — redo tail truncated, command pushed,
      `command_cursor` advanced,
      (c) auto-save trigger via `trigger_auto_save` when
      `auto_save_path` is set,
      (d) full `derivation_cache.clear()` (LD2 precision pending).
      Same rails fire on `undo` / `redo`.

R5.   [DONE] BLAKE3 cache helpers: `sectorforge::rng::digest_bytes` and
      `crate::builder::digest_input` (in `derivation_cache.rs`). Cache
      entries are `{ digest, value }` pairs keyed by the digest of the
      canonical-JSON input slice. Reuses the existing `blake3` workspace
      dep — no new crate.

R6.   [DONE] `builder/src/builder/errors.rs::BuilderError` enumerates every
      required variant (`ValidationFailed`, `InvariantViolated`, `IoFailed`,
      `ParseFailed`, `EntityNotFound`, `StaleSnapshot`) plus transparent
      `Mutation` and `Serde` variants for I/O paths.

R7.   [DONE] `gui-core/src/jobs.rs::JobHandle<T>` uses `std::thread::spawn` plus
      `std::sync::mpsc::channel` for results, `Arc<Mutex<f32>>` for
      progress, and `Arc<AtomicBool>` for cancellation. `JobContext::
      set_progress` calls `egui::Context::request_repaint` on each tick.

R8.   [DONE] `builder/src/builder/command.rs::tests::command_log_determinism_blake3`
      replays a fixed `BuilderCommand` sequence twice and asserts the
      `digest_bytes(serde_json::to_vec(&sector))` hex is equal across runs.

R9.   [DONE] Crate-boundary audit after the split:
      `sectorforge-gui` has no builder dependency and no builder module;
      builder-only dependencies live in `builder/Cargo.toml`;
      shared egui dependencies live in `gui-core/Cargo.toml`;
      cache helpers reuse `sectorforge::rng::digest_bytes`, so neither GUI
      app needs a direct `blake3` dependency for builder cache keys.

R10.  [DONE] Panel convention pinned in `builder/src/builder/panels/mod.rs`:
      every panel is `fn show(ui: &mut egui::Ui, state: &mut BuilderState)`
      — no globals, no `lazy_static`, no raw `String` IDs across the
      boundary, modal state in `BuilderState::modal: Option<ModalKind>`.
      First concrete instance lives in `panels/status.rs` (status bar).

4. DATA-MODEL TASKS (foundation)
================================================================================

D1.   [DONE] `GeneratedSector::empty(id, title, seed, width, height)` constructor
      in `src/sector_model.rs`. Returns valid empty sector that passes
      pre-validation. Required because the builder starts blank.

D2.   [DONE] `GeneratedSystem::new_at(id, coord, name)` and `GeneratedWorld::new(
      id, name)` constructors. Default enum values must be the
      lowest-impact variants (e.g. `Atmosphere::Standard`,
      `TechLevel::Industrial`). Document defaults in doc-comments.

D3.   [DONE] Mutation API on `GeneratedSector` (new module
      `src/sector_model/mutation.rs`):
        - `add_system`, `remove_system`, `move_system`
        - `add_world_to_system`, `remove_world`
        - `add_route`, `remove_route`, `swap_route_endpoints`
        - `add_faction`, `remove_faction`
        - `add_world_presence`, `remove_world_presence`
        - `add_claim`, `remove_claim`
        - `set_system_control_state`, `set_world_dominance`
        - `add_region`, `remove_region`, `add_region_hex`,
          `remove_region_hex`
        - `add_orbital_asset`, `remove_orbital_asset`
        - `add_surface_region`, `remove_surface_region`
        - `set_archetype`, `clear_archetype`
        - `add_intel_record`, `remove_intel_record`
        - `add_history_event`, `remove_history_event`, `edit_event`
        - `set_economy_override`, `clear_economy_override`
        - `set_relation_override`, `clear_relation_override`
      Each method returns `Result<(), MutationError>`. Each method is the
      single canonical entry — no panel mutates fields directly.

D4.   [DONE] Re-index pass (`GeneratedSector::reindex_ids`) manages `sys-NNNN`,
      `sys-NNNN-wNN`, `route-sys-A-sys-B` after structural changes.
      Supports stable IDs across renames using a tombstone table
      (`id_history` in `GeneratedSector`) when `stable_ids_on_rename`
      is enabled in the builder.

D5.   [DONE] `BuilderState` (in `builder/src/builder/state.rs`):
        - `sector: GeneratedSector`
        - `project_path: Option<Utf8PathBuf>` (use `camino`)
        - `config: SectorforgeConfig` (from `src/config.rs`)
        - `data_catalogs: DataCatalogs` (world rows, names, faction rows,
          relation tables, route rules, region defs, economy defs)
        - `index: BuilderIndex`
        - `command_log: Vec<BuilderCommand>` (for undo + replay)
        - `snapshots: Vec<Snapshot>` (named save-points)
        - `pinned_systems: BTreeSet<SystemId>` (side-table for Q1)
        - `pinned_worlds: BTreeSet<WorldId>` (side-table for Q1)
        - `derivation_cache: DerivationCache`
        - `dirty: bool`, `auto_save_path: Option<Utf8PathBuf>`
        - `validation_report: Option<ValidationReport>`
        - `invariant_report: Option<InvariantReport>`
        - `modal: Option<ModalKind>`
        - `pending_jobs: Vec<JobHandle>` (for off-thread work)

D6.   [DONE] Implement `Serialize/Deserialize` for `BuilderState` so the in-progress
      builder session can be saved as `.sgforge`. Use a JSON envelope
      containing base64-encoded files by default to avoid new dependencies.
      Optionally support a `.tar` format toggle for portability if the `tar`
      crate is enabled. Use `serde_json` only; no bincode.

5. PROJECT + I/O TASKS
================================================================================

P1.   [DONE] New project wizard: blank project at `<dir>/`, writes default
      `sectorforge.toml`, empty `worlds.toml`, optional preset overlay.
      `presets::scaffold_to_dir(preset_id, dst, seed_override)` helper added
      in `src/presets.rs`. Wizard panel in
      `builder/src/builder/panels/new_project.rs` drives
      `project_io::new_project` which scaffolds the directory and loads it
      back via the §P2 path so the in-memory state is identical to a fresh
      open.

P2.   [DONE] Open project: parse `sectorforge.toml` via
      `sectorforge::input::load_project`, load all referenced files (worlds,
      names, factions, route_rules, relations, regions, economy, history)
      into `BuilderState::data_catalogs`. Sector loaded from
      `<outputs.directory>/sector.json` when present, else blank empty
      sector matching dimensions. Parse errors surface as
      `BuilderError::ParseFailed { file, message }` — `toml` crate's
      messages already carry `line N, column M` info. Picker panel in
      `builder/src/builder/panels/open_project.rs`.

P3.   [DONE] Save project: writes sectorforge.toml + every present catalog
      back under the project root, then `<outputs>/sector.json` and (when
      `write_manifest` is true) `<outputs>/manifest.json`. Each write is
      atomic via tmp + rename (R9 forbids new crates so we don't use
      `tempfile::NamedTempFile::persist`; the strategy is the same).
      Manifest input_digests are updated in-place to mirror the files we
      just wrote. Action panel in
      `builder/src/builder/panels/save_project.rs` exposes Save and Save-as
      buttons.

P4.   [DONE] Project tree view (new tab `PROJECT`).
      `builder/src/builder/panels/project_tree.rs` renders a collapsible
      directory tree rooted at `BuilderState::project_path`. Folders
      sort-first then alpha; hidden (`.<name>`) entries skipped. Files
      already marked in `BuilderState::dirty_files` render with a leading
      "● " in yellow. Click sets `BuilderState::selected_file` —
      the §PF2 TOML editor tabs (Phase E) will read it to decide which
      buffer to open.

P5.   [DONE] File watcher.
      `builder/src/builder/file_watcher.rs` spawns an mtime-polling thread
      (R9 forbids new crates so we don't take the suggested `notify` dep).
      The watcher samples every file the loader hashed at open-time,
      ticks at 1 Hz, and posts `FileChange { rel_path, mtime }` via
      `mpsc`. The main UI loop drains via
      `project_io::drain_watcher_events`: when the in-memory buffer is
      clean it silently re-parses the affected catalog via
      `project_io::reload_catalog`; when dirty (global `state.dirty` or
      the file is in `dirty_files`) it raises
      `ModalKind::ConflictResolver { rel_path }` and the
      `panels/conflict_resolver.rs` dialog offers Reload-from-disk or
      Keep-in-memory.

P6.   [DONE] Recent projects list in Preferences.
      `builder/src/builder/preferences.rs::Preferences` (`recent_projects:
      Vec<Utf8PathBuf>`) round-trips via
      `~/.config/sectorforge/preferences.toml`. Loaders tolerate missing
      or malformed files. `push_recent` dedupes + bumps to front,
      truncates to 10. Wired into `open_project` and `save_project_as` so
      every successful project hit lands at the top of the MRU. UI lives
      in `panels/preferences.rs` — click an entry to open it.

6. GENERATION CONFIG
================================================================================

G1.   [DONE] Generation panel reaches feature parity with `[generation]` and
      `[generation.placement]` / `[generation.world_selection]` /
      `[generation.routes]` / `[generation.relations]` tables in
      `sectorforge.toml`. Fields:
        seed, sector_width, sector_height, subsector_width,
        subsector_height, system_count, min/max worlds per system,
        allow_empty_hexes, world_feature_count, strict_world_rows,
        placement.mode (uniform_grid|weighted_grid|clustered),
        placement.cluster_bias, placement.minimum_system_distance,
        world_selection.mode, world_selection.require_complete_rows,
        world_selection.allow_partial_rows,
        world_selection.same_star_colour_bias,
        world_selection.strict_same_star_colour,
        world_selection.avoid_duplicate_world_type_in_system,
        routes.enabled, routes.max_route_distance, routes.route_density,
        routes.ensure_connected_graph,
        relations.min_world_presence.
      Implementation: `builder/src/builder/panels/generation.rs::show_g1_parameters`
      binds every listed field to a typed widget (ComboBox over enums,
      DragValue for ints, Slider for fractions) and mutates
      `state.config.generation` directly. The panel is hosted from the
      PROJECT tab as a `Generation (§6)` collapsing header so the §N1
      24-tab strip stays stable.

G2.   [DONE] Seed-lock toggle. When locked, "Re-roll" preserves
      `[generation].seed`; when unlocked, increments via
      `blake3("sectorforge:{seed}:reroll:{n}")`.
      Implementation: `BuilderState::{seed_locked, seed_reroll_counter}`
      plus `BuilderState::reroll_seed` (returns the new seed and rewrites
      `config.generation.seed`). Counter monotonically advances on every
      unlocked re-roll; the digest helper lives at
      `builder/src/builder/preview.rs::derive_reroll_seed`. Tests
      `reroll_locked_keeps_seed`,
      `reroll_unlocked_advances_seed_and_counter`, and
      `derive_reroll_seed_is_deterministic_and_counter_sensitive` pin the
      contract.

G3.   [DONE] Live preview mode: every config edit triggers a debounced
      regeneration (200 ms). Run on worker thread; partial preview into
      a scratch `GeneratedSector` displayed under a "PREVIEW" badge.
      Implementation: `builder/src/builder/preview.rs::PreviewState` owns the
      debounce timer, scratch sector, in-flight `JobHandle`, and a
      revision counter that discards stale results. `PreviewState::pump`
      is called per-frame from the panel; the worker runs
      `sectorforge::generation::generate_with_progress_and_cancel`
      through `sectorforge_gui_core::jobs::spawn_job`. Default debounce =
      `DEFAULT_DEBOUNCE_MS` = 200 ms. The panel surfaces the scratch
      sector counts under a coloured "PREVIEW READY" line.

G4.   [DONE] "Apply" promotes preview to active sector and overwrites
      `BuilderState::sector`. Preserves manual edits to systems flagged
      pinned (resolved per Q1 to a `BuilderState::pinned_systems`
      side-table, not a `GeneratedSystem` field — see Q1 / D5 / S3).
      Implementation: `BuilderState::apply_preview` swaps the scratch
      sector in, then for each `SystemId` in `pinned_systems` restores
      the pre-preview entry at the same id (or re-inserts it if the
      preview dropped the slot). It then rebuilds the index, clears the
      derivation cache, marks the project dirty, and re-runs invariants.

G5.   [DONE] Per-subsector partial regeneration: select a rectangle / cluster of
      hexes, regenerate only those systems. Reuses
      `sectorforge::generate_system_standalone` per slot. Pinned systems
      are skipped. `BuilderState::regions` are exposed via the in-memory
      catalogs the partial regen synthesises into a `ProjectInput`, so
      warp regions affect downstream draws.
      Implementation: `BuilderState::{partial_regen_rect,
      regenerate_partial}` plus `PartialRegenRect::{from_corners,
      contains}`. The panel exposes min/max q/r DragValues; on apply,
      every non-pinned in-rect system is replaced by a fresh
      `generate_system_standalone` call keyed by its existing index.

G6.   [DONE] "New sector from preset" inside the builder — reuses §P1
      logic but keeps the current builder open in a new tab via a new
      `BuilderWorkspace` (`builder/src/builder/workspace.rs`). The
      workspace owns `Vec<BuilderState>` plus an active index;
      `push`/`switch_to`/`close_active` drive the tab strip. The panel
      collects (preset id, destination, seed), calls
      `project_io::new_project` with `preset = Some(id)`, and pushes the
      resulting state into the `BuilderApp` workspace. Library tests and
      non-app callers may still use the fallback path that replaces the
      current state, but the shipping `sectorforge-builder` app always
      provides a workspace. Modal lifecycle uses `ModalKind::NewFromPreset`.

45. WORLDS DATA NATIVE-FIRST (CSV path fully removed)
================================================================================

Rationale: builder pivots to in-app construction. The previous twin-CSV
(`key.csv` + `generator.csv`) was a spreadsheet-import shape — stringly
typed, redundant with the existing enums, no structure for feature
pools, awkward to edit via typed builder widgets. Native model =
typed serde TOML. CSV support — loader, writer, old GUI editor, conversion
command, and `OutputFormat::Csv` — has been removed entirely.

WD1. [DONE] Enum-authoritative variants. Each enum in
     `src/worlds.rs` (StarColour, WorldType, Atmosphere, Temperature,
     Biosphere, Population, TechLevel, Government, NotableFeature)
     exposes `pub const VARIANTS: &'static [Self]`. `KeyTables`
     uses `KeyTables::from_enums()` exclusively to build the full
     table from compiled variants.

WD2. [DONE] Typed `worlds.toml` loader. New file
     `src/worlds_toml.rs`. Defines `WorldsConfig { generation:
     Vec<GenerationRow>, features: FeaturePoolConfig }` with serde
     `Serialize`/`Deserialize`. Loader returns the same
     `(KeyTables, Vec<GenerationRow>)` tuple downstream code expects
     (`world_pool::build_pool` untouched). Sole supported format.

WD3. [DONE] Structured feature pools. `FeaturePoolConfig` carries
     `global`, `by_world_type: BTreeMap<WorldType, Vec<(NotableFeature,
     f64)>>`, `by_star_colour: BTreeMap<StarColour, Vec<...>>`. Maps
     into existing `FeaturePool` at pool-build time. Round-trips
     deterministically (BTreeMap ordering).

WD4. [DONE] Native typed editing foundation. The existing viewer/editor
     `gui/src/data_editor.rs` reads/writes `WorldsConfig` exclusively;
     rows are edited via enum dropdowns (`ComboBox` over `Enum::VARIANTS`)
     and `DragValue<f64>` weights. Builder parity belongs in
     `sectorforge-builder` via PF3 / `builder/src/builder/panels/*`; do not
     route builder world-data editing through `sectorforge-gui`.

WD5. [DONE] CSV removal. Twin-CSV loader, `convert-csv-to-toml`
     CLI/library entry point, old GUI CSV editor view, CSV writers in

     have all been removed. All bundled examples
     (`examples/{big_test,big_sparse_test,llm_test,m42_project}`)
     and the `_base` preset ship `worlds.toml` as the sole source

47. OFF-THREAD RUNNER (Q4 Answered)
================================================================================

Rationale: Keep the UI responsive during heavy computation (generation,
search, complex derivations). Ad-hoc threads avoid the overhead and
complexity of an async runtime when all library code is synchronous.

OTR1. [DONE] Job Infrastructure. 'gui-core/src/jobs.rs' defines 'JobHandle<T>'
      and 'JobContext'. Uses 'std::thread::spawn' for execution.

OTR2. [DONE] Communication. Uses 'std::sync::mpsc' channels for returning
      results and 'Arc<Mutex<f32>>' for shared progress tracking.

OTR3. [DONE] UI Integration. 'JobContext' holds an 'egui::Context' and calls
      'request_repaint()' when progress updates, ensuring the UI stays
      fresh.

OTR4. [DONE] Cancellation. 'JobHandle' includes an 'Arc<AtomicBool>' that

48. LIVE PREVIEW (Q5 Answered)
================================================================================

Rationale: Users need immediate feedback on generation config changes (seed,
density, etc.) without losing their current working sector until they are
ready. Debounced off-thread regeneration ensures the UI stays fluid.

LPV1. [DONE] Debounce Logic. `builder/src/builder/preview.rs::PreviewState`
      includes the debounce timer. Edits reset the timer (200ms). The
      `sectorforge-builder` UI loop spawns the job only after the timer
      expires.

LPV2. [DONE] Scratch Sector. `PreviewState` holds the scratch
      `GeneratedSector`. Background jobs write into this scratch space,
      keeping `BuilderState::sector` untouched until apply.

LPV3. [DONE] Preview UI. The `sectorforge-builder` generation panel shows
      preview readiness/counts and an "APPLY PREVIEW" button to commit the
      scratch sector. Shared rendering helpers may come from
      `sectorforge-gui-core`, but the preview state lives in the builder app.

LPV4. [DONE] Worker Integration. Uses the §47 Job infrastructure to
      run 'sectorforge::generation::generate' without blocking the UI thread.

49. STABLE IDS & TOMBSTONES (Q2 Answered)
================================================================================

Rationale: External references (segmentum manifests, history, manual notes)
break if IDs are aggressively renumbered. The "compat" mode ensures that
renaming or moving entities preserves their identity.

SID1. [DONE] Tombstone Table. 'GeneratedSector' includes an 'id_history'
      BTreeMap mapping original IDs to current IDs.

SID2. [DONE] Re-index Pass. 'GeneratedSector::reindex_ids' supports two modes:
      'sequential' (fills holes, renumbers everything) and 'stable' (preserves
      existing IDs, only assigns to new entities).

SID3. [DONE] Mutation Integration. The core model now resides in
      'src/sector_model/mod.rs' with structural re-indexing in
      'src/sector_model/mutation.rs'.

SID4. [DONE] Builder Setting. `BuilderState` includes `stable_ids_on_rename`
      (default true) to control re-indexing behavior during
      `sectorforge-builder` sessions.
