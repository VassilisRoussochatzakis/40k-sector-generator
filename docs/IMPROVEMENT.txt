================================================================================
EXECUTIVE SUMMARY
================================================================================

Overall health: GOOD. The codebase already follows the REFACTOR.txt spirit in
many places (Arc<str> interning of identifiers in `sector_model`, BTreeMap for
deterministic iteration in generation paths, thiserror SectorError, cooperative
cancellation through `generate_with_progress_and_cancel`, `Drop` impl on
`FileWatcher`, revision-tagged GUI preview, per-bin clap CLI). No `unsafe`, no
`Box<dyn>` plumbing, no `todo!()`/`unimplemented!()` anywhere.

What needs work, in priority order:

  P0  Correctness:  derivation_cache digest swallows serialization errors;
                    settings_digest covers only 7 fields out of dozens that
                    actually change generated output.

  P1  Test gap:     PNG / SVG renderer has byte-stable golden tests for the
                    egui UI map (gui-core/tests/map_snapshots.rs) but no
                    pixel-hash test for the public `bitmap::write_sector_png_*`
                    / `system_map::write_one_system_png` writers. Renderer
                    refactors can silently shift output.

  P1  Bench gap:    benches/generation.rs only covers generate / validate.
                    Hash/overlay/raster/encode/JSON phases are not benched, so
                    regressions are invisible per phase.

  P2  Cleanup:      cargo fmt --check fails on several files; clippy reports
                    10 default warnings and ~430 pedantic warnings concentrated
                    in ~6 categories that are safe to autofix.

  P2  GUI:          gui-core::jobs::JobHandle<T> is the real abstraction; the
                    builder::state::JobHandle (id/description only) is a stub
                    nobody uses for real work — drop or unify.

  P3  Ergonomics:   src/main.rs is 1809 LOC in one file; SectorError and
                    SectorProgress lack #[non_exhaustive]; CLI progress logging
                    is a 300-line match.

Things NOT to change yet:
  - Public re-export shape in lib.rs (135 pub items): downstream consumers
    likely pin these by path. Trim only with a deprecation cycle.
  - Big enum `SectorProgress` (~27 variants): boxing inside the enum doesn't
    win anything since it travels through a `FnMut` callback by reference;
    only large_enum_variant on PreviewJobResult is worth a Box.
  - `worlds::KeyTables`'s HashMap fields are read-only lookups and are never
    iterated for output; leave as-is unless we later add iteration there.

P0-1  derivation_cache::digest_input swallows serialization errors  [IN PROGRESS]
────────────────────────────────────────────────────────────────────────────────
File:    builder/src/builder/derivation_cache.rs:59-62
Current:
    pub fn digest_input<T: Serialize>(input: &T) -> String {
        let bytes = serde_json::to_vec(input).unwrap_or_default();
        digest_bytes(&bytes)
    }

Problem:
  Any input whose `Serialize` impl fails hashes the empty byte string. Distinct
  failed inputs collide on a single digest and can read back another input's
  cache entry. (OPTIMIZE.txt #3.)

Recommendation:
  Return `Result<String, serde_json::Error>` (or wrap it in a new
  `BuilderError::DigestFailed` variant). At call sites, skip caching on error
  and surface to the status panel — never silently key on `""`.

  Optional belt-and-braces: in `CacheEntry`, store the digest as a strong
  type (e.g. `[u8; 32]`) to forbid the empty-string-as-digest case at the
  type level.

Validation:
  Unit test with a `Serialize` impl that returns an error: assert
  `digest_input` returns `Err`, assert no cache write occurs.

P0-2  settings_digest is narrower than its name implies  [IN PROGRESS]
────────────────────────────────────────────────────────────────────────────────
File:    src/generation.rs:2027-2040
Current:
    let settings_repr = format!(
        "{}-{}-{}-{}-{}-{}-{}",
        config.generation.seed,
        config.generation.sector_width,
        config.generation.sector_height,
        config.generation.system_count,
        config.generation.min_worlds_per_system,
        config.generation.max_worlds_per_system,
        config.generation.world_feature_count,
    );

Problem:
  Generated output depends on `route_rules`, `regions`, `economy`, `history`,
  `world_selection`, authored features, and several OutputConfig knobs (per
  REFACTOR.txt Section 3.J/L on canonical config). All of those can change
  while `settings_digest` stays constant, so manifest identity is weaker than
  callers assume. (OPTIMIZE.txt #4.)

Recommendation:
  Hash a canonical Serializable struct that includes every config slice that
  influences sector output:
    - generation
    - route_rules (RouteRules)
    - regions config
    - economy config
    - history config
    - relations config
    - world_selection (overlay tags)
    - any output toggles that change written bytes
  Version the digest payload as `settings_digest_v2` (keep the old field
  empty/optional or kept under `settings_digest_legacy` for one release).
  Use `serde_json::to_vec` over a `&CanonicalSettings` newtype with BTreeMap
  fields only — never HashMap — to guarantee byte stability.

Validation:
  - Snapshot: assert the digest of a known fixture matches a checked-in hex.
  - Regression tests: changing any one of route relations threshold, region
    enablement, economy enablement, world_selection.tag_overlay weights flips
    the digest; changing a pure formatting/output knob that does NOT affect
    output does not.

P2-4  Lock-on-progress JobHandle is heavier than needed  [IN PROGRESS]
────────────────────────────────────────────────────────────────────────────────
File:    gui-core/src/jobs.rs:11, 27, 47, 75
Current: `progress: Arc<Mutex<f32>>` and `cancelled: Arc<AtomicBool>`.

Problem:
  Every `set_progress` call locks a Mutex and triggers a repaint. Hot inner
  loops in generation (e.g. `RouteControlsProgress`) may call set_progress
  per-route — the lock is uncontended but not free, and the repaint
  request to egui is throttled on the egui side but still costs.

Recommendation:
  - Store progress as `Arc<AtomicU32>` holding `f32::to_bits` / `from_bits`.
    Reads and writes become a single atomic op; no Mutex; no poisoning.
  - For cancellation, downgrade `Ordering::SeqCst` to `Ordering::Acquire`
    on the reader (`is_cancelled`) and `Ordering::Release` on the writer
    (`cancel`). The progress-flag and cancel-flag are independent so SeqCst
    serialization is overkill.
  - Optional: have `set_progress` rate-limit `ctx.request_repaint()` to,
    say, 30 Hz so a tight loop of 10k progress ticks doesn't queue 10k
    repaints. (egui collapses duplicate repaint requests but the cost of
    the call itself adds up.)

P2-5  Builder snapshot deep-clones the full sector  [IN PROGRESS]
────────────────────────────────────────────────────────────────────────────────
File:    builder/src/builder/snapshot.rs:7-12, builder/src/builder/state.rs:992
Current:
    pub struct Snapshot { pub sector: GeneratedSector, ... }
    self.snapshots.push(Snapshot::new(name, self.sector.clone(), ...));

Problem:
  Each named snapshot is a full deep-clone of `GeneratedSector` including all
  `Vec<GeneratedSystem>` content (Arc<str> fields are cheap, the system/world
  vecs are not). With a capped command_log of 200 + multiple snapshots, a
  large sector quickly becomes the largest memory consumer.

Recommendation:
  - Store snapshots as `Arc<GeneratedSector>`. The active state continues to
    own a value `GeneratedSector`; on snapshot, wrap the current value in
    an Arc and share. When the user mutates after a snapshot,
    `Arc::make_mut` deep-clones only on actual write (copy-on-write).
  - Then `Vec<Snapshot>` is effectively `Vec<{ name, Arc<GeneratedSector>,
    command_log_position }>` — duplicated snapshots cost one Arc bump.

  Defer until a profile shows this matters; documented here as the obvious
  next step if memory becomes a concern on large sectors.

P3-1  Public enums lack #[non_exhaustive]  [IN PROGRESS]
────────────────────────────────────────────────────────────────────────────────

  case-by-case). This is itself a breaking change for `match` callers but is
  cheap to land while the public-API consumer set is small.
