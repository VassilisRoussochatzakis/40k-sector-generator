# NEW.md — Proposed New Features for `sectorforge`

This document proposes new features for `sectorforge`, based on the current overview of the application. The suggestions are designed to fit the existing philosophy of the project: deterministic generation, data-driven configuration, rich political state, reproducible exports, and a workflow that supports both command-line pipelines and interactive GUI editing.

The application already has a strong foundation: deterministic sector generation, layered world and faction modelling, route control, subsectors, simulation-adjacent state, GUI editing, validation, and multiple export formats. The highest-value next features should therefore avoid simply adding more random tables. Instead, they should deepen the relationships between existing entities, make generated sectors easier to use in campaigns, and preserve reproducibility.

---

## 1. Historical Timeline and Sector Chronicle Generator (DONE)

A major missing layer is history. The current model can describe what a sector looks like now, but it does not yet explain how it became that way. A deterministic historical timeline would turn the sector from a static political snapshot into a setting with inherited grudges, old treaties, failed crusades, lost colonies, lingering catastrophes, and faction memories.

This feature would generate a `SectorChronicle` after the structural sector exists. It would produce dated or era-labelled events, each referencing existing systems, worlds, routes, factions, claims, subsectors, and anomalies. Events should not be free-floating lore paragraphs; they should be typed records that downstream tools can use.

Example event types:

- `Founding` — settlement of a world, establishment of a subsector capital, discovery of a stable warp lane.
- `Compliance` — incorporation of a world into Imperial administration or another sovereign structure.
- `Schism` — religious, political, dynastic, or ideological fracture.
- `War` — inter-faction campaign affecting one or more systems.
- `Blockade` — origin story for an existing blockade or route-control imbalance.
- `Plague` — famine, mutation wave, techno-virus, warp contagion, or xenos pathogen.
- `Crusade` — sector-level military intervention that explains current military presences.
- `Disappearance` — lost expedition, vanished system, sealed route, abandoned station.
- `Rebellion` — precursor to current contested control or claims.
- `Treaty` — explanation for legal sovereignty versus practical occupation.
- `Awakening` — Necron tomb activation, daemon-world emergence, Tyranid tendril arrival, or cult uprising.

Each event should include stable IDs, a deterministic date or relative era, participating factions, affected entities, consequences, and a short generated prose summary. The event list should be sorted deterministically. The prose can be assembled from templates rather than generated by an external model, preserving offline use and byte-identical output.

A useful schema might look like:

```toml
[[history.eras]]
id = "age_of_compliance"
label = "Age of Compliance"
relative_start = -900
relative_end = -650
weight = 1.0
allowed_events = ["Founding", "Compliance", "Treaty"]

[[history.event_rules]]
when_system_state = "Warzone"
prefer_event = "War"
minimum_events = 1
```

The generator could derive the chronicle from current state. For example, if a world has `Legal Sovereignty` claimed by the Imperium but is currently occupied by Chaos, the chronicle can generate an earlier compliance event, a later invasion, and a still-unresolved mandate. If a route is perilous, hidden, or heavily interdicted, the chronicle can explain whether it was always dangerous or became unsafe after a named disaster.

The GUI should expose this as a timeline panel. Clicking an event should highlight affected systems and routes on the map. Clicking a world should show all historical events that mention it. The Markdown export should gain a "Sector History" chapter, and per-system Markdown should include local history.

Why this matters: history is the bridge between procedural data and campaign usability. A GM can already see that a world is contested; with this feature, they can also answer why the war started, who remembers the old treaty, and what unresolved wound the players can interact with.

## 2. Campaign Fronts and Active Story Arcs

The current simulation layer tracks conflict, stability, archetypes, intel, and power projection, but it does not appear to bundle those elements into campaign-ready arcs. A `CampaignFront` system would convert sector state into a small number of active narrative pressures that a GM can actually run.

A front is an organized threat, opportunity, or crisis with a goal, actors, affected locations, visible signs, escalation stages, and possible outcomes. It should be derived from the existing model rather than manually invented from scratch.

Example fronts:

- **A Genestealer cult nearing open uprising** across three mining and hive worlds.
- **A Rogue Trader commercial coup** against a weak planetary governor along a profitable trade route.
- **A Chaos corruption wave** spreading through shrine worlds and unstable warp lanes.
- **A Mechanicus resource annexation** targeting mining worlds and orbital shipyards.
- **An Ork Waaagh! migration front** moving through fringe systems.
- **A subsector succession crisis** where legal sovereignty, dynastic claims, and popular authority disagree.
- **A naval interdiction campaign** where route control, piracy, and blockade fleets collide.

Each front could have a schema like:

```json
{
  "id": "front-0007",
  "kind": "cult_uprising",
  "title": "The Ash-Gene Revelation",
  "primary_faction": "fac-genestealer-ash-brood",
  "opposition": ["fac-imperial-governorate", "fac-ecclesiarchy"] ,
  "systems": ["sys-0003", "sys-0014", "sys-0022"],
  "worlds": ["sys-0003-w01", "sys-0014-w02"],
  "stage": 3,
  "clock": 5,
  "visibility": "suspected",
  "stakes": ["loss_of_agri_exports", "subsector_rebellion"],
  "next_escalations": ["sabotage_orbital_lift", "assassinate_confessor"]
}
```

The front generator should use explicit rules. For instance, if a faction has high covert power, low public legitimacy, hidden dominance, and growing conflict momentum, it is a candidate for an infiltration front. If a system has high industrial value, weak sovereignty, and nearby Mechanicus power projection, it is a candidate for an annexation front.

The feature should include both generated fronts and editable fronts. Generated fronts would be reproducible from the seed. Edited fronts would live in `SectorSave`, since they represent campaign runtime state. Advancing a sector tick could advance front clocks, but only through deterministic rules keyed to the save state.

The GUI could add a "Fronts" tab with filters by faction, affected subsector, visibility, and urgency. The map could draw front overlays: shaded affected regions, arrows for expansion, warning icons for flashpoints. Markdown export should include a GM-facing section with full details and an optional player-facing redacted section based on intel.

Why this matters: a sector generator gives breadth; campaign fronts give direction. This feature would help users turn a complex generated sector into playable session material without making the application into a full game system.

## 3. Quest, Mission, and Rumour Seed Generator (DONE)

Sectorforge already produces the raw ingredients for adventures: contested worlds, hidden masters, route hazards, claims, blockades, cult activity, faction presences, unstable systems, and intel gaps. A mission seed generator would transform those ingredients into actionable hooks.

This feature should create structured `MissionSeed` records. They should be deterministic, typed, and grounded in sector entities. The goal is not to write full adventures, but to produce strong prompts that reference actual generated locations and factions.

Mission types might include:

- `Investigate` — uncover hidden faction presence, anomalous stability collapse, missing ships, false intel.
- `Escort` — move cargo, pilgrims, nobles, prisoners, relics, or refugees along risky routes.
- `Sabotage` — disable orbital assets, manufactoria, communications, cult infrastructure, blockade logistics.
- `Diplomacy` — negotiate claims, treaties, dynastic succession, trade access, or ceasefires.
- `Assassination` — remove warlords, cult magi, corrupt governors, pirate captains, or heretek savants.
- `Recovery` — retrieve relics, lost manifests, STC fragments, black-box logs, gene-samples, or sealed warrants.
- `Defense` — protect a shrine, convoy, system capital, agri-harvest, or evacuation route.
- `Exploration` — survey uncharted systems, hidden routes, void stations, dead worlds, or anomalous regions.

A mission seed should include:

- Hook title.
- Patron faction or individual role.
- Target faction or obstacle.
- Primary location.
- Secondary location, if travel is involved.
- Route requirement, if relevant.
- Public objective.
- Hidden complication.
- Reward or leverage.
- Consequences if ignored.
- Suggested scale: one-shot, short arc, campaign arc.
- Visibility: public, restricted, secret, misinformation.

Example:

```json
{
  "id": "mission-0031",
  "type": "escort",
  "title": "The Tithe Convoy Through Saint Veyr's Gap",
  "patron": "fac-administratum",
  "primary_location": "sys-0012-w02",
  "destination": "sys-0004-w01",
  "route_ids": ["route-sys-0012-sys-0008", "route-sys-0008-sys-0004"],
  "public_objective": "Escort sealed tithe containers to the subsector capital.",
  "hidden_complication": "One container carries an inquisitorial prisoner whose existence is denied.",
  "if_ignored": "The receiving hive enters famine and rebellion rises by one stage."
}
```

The generator can select mission seeds from high-tension areas: worlds with close control scores, unstable routes, mismatched claims, hidden masters, strong faction rivalries, or divergent intel. A user should be able to configure mission density and allowed mission types in TOML.

In the GUI, mission seeds should appear in a sortable table and on map pins. A GM could mark seeds as accepted, completed, failed, hidden, or archived; those changes should live in `SectorSave`. Markdown exports should support `--gm` and `--player` modes so hidden complications can be included or redacted.

Why this matters: this is one of the most immediately useful features for actual play. It makes the tool more than a map and data generator; it becomes a campaign preparation assistant while staying within the existing "not a game" boundary.

## 4. Resource, Tithe, and Strategic Value Model (DONE)

The existing world model includes population, tech level, economy, industry, and government, but a sector intended for 40k-style play would benefit from an explicit resource and tithe layer. This would give concrete reasons factions care about particular worlds and routes.

Each world could gain a `strategic_output` block. The values should be derived from world type, population, tech level, notable features, stability, and faction control. They do not need to be exact economic simulation; they should be normalized scores or bands that support story and map logic.

Suggested resource dimensions:

- `food` — agri output, fisheries, vat production, corpse-starch capacity.
- `ore` — mining, promethium, rare minerals, adamantine, void-harvested resources.
- `manufacturing` — general industrial output.
- `arms` — military production, forge capacity, munitions.
- `ships` — shipyard and orbital construction capacity.
- `pilgrimage` — shrine traffic, relic tourism, ecclesiastical influence.
- `psyker_tithe` — black ship relevance and sanctioning pipeline.
- `manpower` — guard regiments, conscripts, penal levies, voidsmen.
- `knowledge` — archives, forbidden research, scholastica, Mechanicus data-vaults.
- `xenos_value` — alien ruins, biomatter, webway access, tomb complexes.

The sector could then compute dependencies. Hive worlds should depend on food imports. Forge worlds should depend on ore, promethium, and labour. Shrine worlds might depend on pilgrimage routes and protection. If a route is blockaded, downstream systems can receive `shortage_risk` or `tithe_failure_risk`.

This would enable new derived states:

- `tithe_status`: surplus, adequate, strained, delinquent, failed, falsified.
- `supply_risk`: stable, vulnerable, disrupted, collapsing.
- `strategic_priority`: low, local, subsector, sector, crusade-level.
- `dependency_edges`: which systems materially rely on which others.

The CLI could expose `analyze-economy` or `analyze-tithes`, producing a report of critical supply chains. The route planner could add a "strategic" metric that prefers routes carrying high-value goods but penalizes instability and piracy. The GUI could add heatmaps for food surplus, industrial output, tithe stress, and supply vulnerability.

This feature should be data-driven. Project authors should be able to define output rules per world type and notable feature:

```toml
[resources.world_type.AgriWorld]
food = 90
manpower = 20
manufacturing = 5

[resources.notable_feature.TradeHub]
trade_multiplier = 1.4
supply_resilience = 10
```

Why this matters: political conflict becomes more legible when players understand what is at stake. A warzone forge world is not just another red icon; it is the reason three nearby guard regiments lack ammunition.

## 5. Diplomatic Relations and Faction Attitude Matrix (DONE)

Factions currently have kind, disposition, preferences, presence, power, and control, but their relationships to each other appear mostly implicit. A deterministic faction relationship matrix would make the political layer richer and provide a foundation for alliances, proxy wars, ceasefires, trade pacts, vendettas, and uneasy cooperation.

This feature would compute `FactionRelation` records for every relevant faction pair. It should not require every pair to have a bespoke authored relationship. Instead, base attitudes can be derived from faction kind, disposition, claims conflicts, route-control competition, historical events, and world-level overlap.

Suggested relation dimensions:

- `attitude`: allied, friendly, transactional, suspicious, hostile, existential_enemy.
- `trust`: 0–100.
- `fear`: 0–100.
- `rivalry`: 0–100.
- `ideological_distance`: 0–100.
- `economic_dependency`: 0–100.
- `military_pressure`: 0–100.
- `covert_activity`: 0–100.
- `treaty_status`: none, pact, truce, vassalage, charter, nonaggression, vendetta.
- `public_stance` versus `secret_stance`.

The matrix should support asymmetry. A planetary governor may publicly trust the Inquisition while secretly fearing it. A cult may hate the Imperium, while the Imperium may not yet know the cult exists. A Rogue Trader may be friendly toward a forge world for economic reasons while the Mechanicus sees the dynasty as a tolerated nuisance.

Project data should allow overrides:

```toml
[[relations.overrides]]
a = "fac-house-vorn"
b = "fac-rogue-trader-cassian"
public_attitude = "friendly"
secret_attitude = "hostile"
reason = "Succession debt and a disputed charter"
```

The GUI could include a relationship graph view. Nodes would be factions; edges would be colored or styled by attitude, with filters for public, secret, military, economic, or ideological relations. The system view could show local relations only among factions present there. Markdown export should include a faction diplomacy chapter and per-faction dossiers.

This feature also improves other systems. Campaign fronts can use hostile relation pairs. Mission seeds can draw on rivalries. Intel redaction can hide secret relationships. Historical timelines can explain why a vendetta exists.

Why this matters: 40k-style sectors are not just maps of holdings; they are webs of suspicion, mandate, rivalry, and dependence. A relation matrix makes that web explicit.

## 6. Named NPCs, Offices, and Institutional Chains of Command

The current model has factions, governments, and claims, but not named people or offices. Adding a deterministic `Personage` and `Office` layer would make generated sectors easier to run and write about. It would answer questions like: Who is the planetary governor? Which admiral controls the blockade? Who leads the cult? Which cardinal disputes the subsector capital's authority?

This feature should separate offices from office-holders. An office is a durable institutional role; a personage is the current individual occupying it. This matters because campaign state can kill, replace, disgrace, promote, or corrupt a person without deleting the institution.

Example offices:

- Planetary Governor.
- Lord Militant.
- Subsector Prefect.
- Cardinal-Astral.
- Fabricator-Locum.
- Rogue Trader Patriarch or Matriarch.
- Fleet Admiral.
- Inquisitorial Legate.
- Cult Magus.
- Pirate Prince.
- Xenos Envoy.
- Dynasty Heir.

Example personage fields:

```json
{
  "id": "npc-0142",
  "name": "Severine Korda",
  "office_id": "office-sys-0008-governor",
  "faction_id": "fac-imperial-governorate",
  "home_world_id": "sys-0008-w01",
  "traits": ["severe", "indebted", "paranoid"],
  "public_loyalty": "fac-imperial-governorate",
  "secret_loyalty": "fac-rogue-trader-cassian",
  "competence": 63,
  "corruption": 41,
  "ambition": 78,
  "leverage": ["dynastic_debt", "sealed_pardon"]
}
```

Names should use project-supplied name pools, just as systems and worlds do. Offices should be derived from world government, faction presence, control summaries, orbital assets, and subsector capitals. Not every world needs a full cast; the user should configure density.

This feature should integrate with the GUI through a dossier panel. Clicking a world could show its key office-holders. Clicking a faction could show its leadership, agents, rivals, and compromised assets. Campaign Save should allow NPC status changes such as alive, missing, dead, promoted, corrupted, exposed, or replaced.

Markdown exports could gain a "Dramatis Personae" chapter. Per-system Markdown could list the most important local figures. Mission seeds could reference NPCs as patrons, targets, informants, hostages, or rivals.

Why this matters: named individuals are how players emotionally connect with a sector. Factions create structure; NPCs create scenes.

## 7. Planetary Site and Point-of-Interest Generator (DONE)

The overview states that the application is not a tactical map generator, and that boundary should remain. However, there is room for an intermediate layer between whole worlds and battlefields: named planetary sites. These are not hex maps or dungeon layouts; they are campaign-scale points of interest.

A `WorldSite` layer would generate locations within surface regions. Each site would have a type, controlling faction, secrecy, condition, hooks, and links to other systems. This would make worlds feel less abstract and give missions concrete destinations.

Example site types:

- Governor's palace.
- Cathedral-spire.
- Manufactorum district.
- Underhive sump-city.
- Void elevator.
- Star fort dockyard.
- Quarantine zone.
- Xenos ruin.
- Pilgrim necropolis.
- Astropathic choir.
- Arbites precinct fortress.
- Data-vault.
- Shrine of disputed authenticity.
- Penal mine.
- Black market enclave.
- Cult safehouse.
- Crashed voidship.

Each site should be derived from world type, government, notable features, factions, stability, and surface regions. A shrine world should naturally produce cathedrals, reliquaries, pilgrim roads, and heresy investigation sites. A forge world should produce manufactoria, noosphere vaults, maglev arteries, and contaminated labour zones. A death world should produce fortified landing zones, research stations, and hunting preserves.

Suggested schema:

```json
{
  "id": "site-sys-0017-w02-004",
  "world_id": "sys-0017-w02",
  "region_id": "region-sys-0017-w02-north-hive",
  "type": "underhive_cult_safehouse",
  "name": "The Ninth Sump Chapel",
  "known_to": ["fac-genestealer-brood", "fac-inquisition-cell"],
  "public_status": "abandoned",
  "actual_status": "active",
  "controlling_faction": "fac-genestealer-brood",
  "tags": ["hidden", "ritual", "smuggling_access"]
}
```

The GUI could show sites inside the world detail panel, grouped by region and filtered by visibility. The mission seed generator could target a site instead of a whole world. Intel records could redact hidden sites. Markdown exports could include only known sites in player-facing mode.

Why this matters: a sector can be politically rich but still hard to turn into a session. Sites provide the missing granularity: places characters can actually visit.

## 8. Threat Propagation and Crisis Forecasting

The simulation layer includes conflict ticks, stability state, archetype state, power projection, and influence fields. A valuable next step would be a forecasting tool that predicts likely future crises without requiring the application to become a game.

This feature would generate `CrisisForecast` records. Forecasts are not guaranteed outcomes; they are deterministic risk assessments based on current state. They answer: where is the sector likely to break next?

Forecast types could include:

- Rebellion risk.
- Cult uprising risk.
- Famine risk.
- Warp route collapse risk.
- Blockade escalation risk.
- Ork Waaagh! convergence.
- Tyranid incursion pressure.
- Necron awakening cascade.
- Chaos corruption spread.
- Imperial purge likelihood.
- Trade collapse.
- Subsector secession.

A forecast should include risk score, confidence, contributing factors, affected entities, likely trigger, likely consequence, and recommended intervention points. For example:

```json
{
  "id": "forecast-0020",
  "type": "famine_risk",
  "risk": 82,
  "confidence": 71,
  "affected_systems": ["sys-0006", "sys-0009"],
  "drivers": ["agri_route_blockaded", "hive_population_extreme", "piracy_high"],
  "trigger": "Loss of the Calthrax grain convoy",
  "consequence": "Public order collapse and rebellion clock advance",
  "interventions": ["secure_route", "negotiate_tithe_delay", "break_blockade"]
}
```

This feature should be exposed through CLI reports and GUI heatmaps. The GUI could offer a "Forecast" layer where high-risk systems pulse or display warning badges. Clicking a forecast would show a causal explanation, not just a score.

The strongest part of this feature would be explainability. Since the application already emphasizes validation and deterministic derivation, forecasts should list their drivers and formula components. Users need to know why a world is flagged as high risk so they can decide whether the result is narratively useful.

Why this matters: generators are often good at producing state but weak at identifying significance. Crisis forecasting helps users prioritize which parts of a large sector deserve attention.

## 9. Player-Facing Redaction Profiles and Briefing Packs (DONE)

The existing intel and fog-of-war system already supports asymmetric information, and Markdown export can produce human-readable documents. The natural next feature is configurable briefing packs for different audiences.

A `BriefingProfile` would define what a reader is allowed to see. Profiles could be tied to a faction, an NPC office, a campaign role, or an arbitrary security level. The exporter would then produce redacted Markdown, JSON, CSV, or PNG outputs from that perspective.

Example profiles:

- `gm_full_truth` — everything.
- `imperial_navy_captain` — routes, orbital assets, known warzones, suspected piracy, limited ground politics.
- `inquisitorial_cell` — hidden presences above a confidence threshold, corruption forecasts, secret claims, cult traces.
- `rogue_trader_dynasty` — trade values, route hazards, toll authorities, market opportunities, hostile patrols.
- `local_governor` — own world, nearby systems, official sovereignty, no hidden masters unless detected.
- `player_public_atlas` — safe public sector gazetteer with propaganda and omissions.

A profile might be configured as:

```toml
[briefing_profiles.inquisitorial_cell]
observer_faction = "fac-inquisition"
include_hidden_routes = true
minimum_intel_confidence = 40
show_secret_relations = true
redact_unknown_factions = true
export_formats = ["markdown", "png", "json"]
```

The redaction engine should work consistently across formats. If a hidden route is unknown in Markdown, it should also be absent or marked unknown in JSON and not drawn on PNG maps for that profile. Redacted outputs should include a manifest indicating the profile used, so users know exactly what perspective an export represents.

The GUI could allow profile switching in the map view. This would be extremely useful: the same sector map could look different to the Imperial Navy, a criminal syndicate, or an Aeldari observer. The map could show false or suspected information using distinct visual styles, such as dashed routes, uncertain faction glyphs, or blurred control colors.

Why this matters: the application already models hidden information; briefing packs make that information usable at the table and in campaign handouts.

## 10. Scenario Diffing and Seed Comparison Tools

One of the core workflows is re-rolling seeds until the sector feels interesting. However, users currently need to inspect outputs manually. A seed comparison and diffing tool would make iteration much faster.

This feature would compare two generated sectors, two saves, or two configurations and produce a structured difference report. It should understand sector semantics rather than simply diffing JSON text.

Comparison modes:

- `seed-diff` — same project data, different seeds.
- `config-diff` — same seed, changed generation settings.
- `data-diff` — same seed, changed input CSV/TOML data.
- `save-diff` — same static sector, different campaign save states.
- `version-diff` — same inputs, different generator version.

Useful metrics:

- System count, world count, route count, subsector count.
- Faction power deltas.
- Number of warzones, blockades, infiltrated systems, quarantines.
- Strategic resource surplus or shortage changes.
- Route graph connectivity and average travel risk.
- Top changed worlds by control score.
- New or removed dominant factions.
- Changes in subsector capitals.
- Output digest changes from manifest comparison.

The tool should produce both machine-readable JSON and human-readable Markdown. A CLI command might look like:

```bash
sectorforge compare \
  --left out/seed-a/sector.json \
  --right out/seed-b/sector.json \
  --format markdown \
  --output diff.md
```

The GUI could provide a side-by-side comparison view: two maps, synchronized pan and zoom, with changed systems highlighted. A summary panel could rank the most narratively significant differences.

This feature should also help preserve determinism. If a new generator stage is added, users may want to verify that old stages remain stable. A semantic diff can report whether only the new feature block changed or whether existing systems, worlds, or routes changed unexpectedly.

Why this matters: deterministic generation is powerful, but iteration becomes more powerful when users can compare outcomes intelligently.

## 11. Mod Packs, Data Packages, and Dependency Management

The project is intentionally data-driven, with editable CSV/TOML files for world taxonomy, names, factions, routes, and generation policy. As projects grow, users will want to share and reuse data sets. A mod-pack system would formalize this.

A `sectorforge-pack.toml` manifest could describe a reusable data package: name lists, faction sets, world tables, route modifiers, export themes, briefing profiles, and validation rules. Projects could depend on one or more packs and override specific records locally.

Example pack manifest:

```toml
[pack]
id = "gothic-frontier-core"
name = "Gothic Frontier Core"
version = "1.2.0"
author = "Example Author"
sectorforge_min_version = "0.8.0"

[contents]
world_key = "worlds/key.csv"
world_generator = "worlds/generator.csv"
factions = "factions.toml"
system_names = "names/systems.toml"
world_names = "names/worlds.toml"
routes = "routes.toml"
```

The project config could then include:

```toml
[packs]
use = ["gothic-frontier-core", "ork-wars-expansion"]
```

Important design questions:

- How do packs merge weighted tables?
- How are duplicate IDs handled?
- Can a project disable records from a pack?
- How are pack file digests included in the manifest?
- Can packs declare compatibility ranges?
- Are packs loaded from local folders only, or can users configure registries later?

For the first implementation, local folder packs are enough. Avoid networked package management at first; the overview explicitly notes the application is not networked, and local packs fit the existing offline workflow.

The GUI could include a pack manager that lists installed local packs, validates them, previews contents, and shows which project records override pack records. The inspector command could gain `inspect-pack`.

Why this matters: a data-driven generator becomes much more useful when communities can share curated data foundations without copying huge folders by hand.

## 12. Schema Versioning, Migration, and Compatibility Reports

The manifest records generator version and input digests, and validation protects invariants. As the JSON schema grows, the project would benefit from explicit schema versioning and migration tools.

This feature would assign version numbers to major serialized structures: `Sector`, `System`, `World`, `Faction`, `Route`, `SectorSave`, and future structures such as `CampaignFront`, `MissionSeed`, or `SectorChronicle`. The application should be able to read older supported versions, migrate them forward, and produce a report of changes.

A migration command could look like:

```bash
sectorforge migrate-sector \
  --input old/sector.json \
  --output migrated/sector.json \
  --report migrated/migration-report.md
```

The migration report should include:

- Source schema version.
- Target schema version.
- Fields added with default values.
- Fields renamed.
- Deprecated fields removed.
- Any lossy transformations.
- Validation results after migration.
- Manifest updates.

`SectorSave` migration is especially important because saves may represent campaign progress. Users will tolerate regenerating static sectors, but they will care deeply about preserving session history, edited claims, front clocks, NPC states, and completed missions.

The GUI should detect older files and offer to migrate a copy rather than overwrite the original. The CLI should support strict mode, refusing lossy migrations unless explicitly allowed.

Why this matters: the proposed feature set adds many new serialized structures. Without migration support, every major update risks breaking users' existing campaign archives.

## 13. Themeable Map Rendering and Symbol Sets (DONE)

The bitmap export is already useful, with hex grids, systems, routes, faction tinting, subsector borders, legends, glyphs, and integer scale. A theme system would let users produce maps for different purposes without changing sector data.

A map theme should control visual presentation only. It should not affect generation. Theme files could specify colors, line weights, glyph sets, label policies, legend style, route styles, heatmap palettes, and whether to prioritize readability or atmosphere.

Possible built-in themes:

- `gm_dark` — high-contrast operational map for screen use.
- `print_mono` — black-and-white printable map.
- `imperial_archive` — parchment/gazetteer style.
- `navis_tactical` — route-first naval chart.
- `inquisition_redacted` — classified briefing style with hidden data marks.
- `subsector_political` — strong borders and faction coloring.

Example config:

```toml
[map_theme]
name = "navis_tactical"
background = "#05070a"
show_subsector_borders = true
route_line_mode = "hazard_weighted"
label_density = "important_only"
legend = "compact"
```

For safety and portability, the project should continue to avoid external font requirements unless explicitly configured. The embedded font can remain the default. Optional custom fonts should be referenced by path but never embedded into shared output bundles unless licensing is clear.

The GUI could expose theme selection in the map view and export dialog. CLI exports could accept `--theme`. The manifest should record the theme file digest for PNG outputs.

Why this matters: different workflows need different maps. A GM screen, a player handout, a printed poster, and a VTT background have different visual requirements.

## 14. Web/VTT Export Adapters

The overview mentions downstream integration with campaign trackers, web maps, virtual tabletops, and wikis. The existing JSON/Markdown/CSV/PNG exports are a good base, but dedicated adapters would reduce friction for common workflows.

This feature should add optional export adapters that transform a sector into directory structures expected by other tools. Because VTTs and wikis change over time, adapters should be modular and versioned separately from the core schema.

Potential adapters:

- `obsidian` — Markdown vault with links between systems, worlds, factions, routes, NPCs, missions, and fronts.
- `static-web` — self-contained HTML/JS map bundle using exported JSON.
- `foundry-vtt` — journal entries and map assets formatted for import.
- `roll20` — image assets and handout Markdown.
- `generic-wiki` — one Markdown file per entity with frontmatter.
- `geojson-like` — spatial-ish export for custom web map renderers, even though the grid is hex-based rather than geographic.

The safest first adapter would be Obsidian or generic Markdown wiki export. It can be fully offline, deterministic, and does not require tracking an external API. Each entity page could include stable links:

```markdown
# System Aurelia

- Coordinates: 12, 7
- Subsector: [[Subsector Aurelia]]
- Worlds: [[Aurelia I]], [[Aurelia II]]
- Routes: [[Route Aurelia--Vorn's Reach]]
- Dominant faction: [[House Vorn]]
```

The exporter should allow redaction profiles, so users can generate a GM vault and a player vault from the same sector.

Why this matters: many users will not consume raw JSON directly. Tool-specific adapters make the generator easier to slot into real campaign workflows.

## 15. Constraint-Based Generation and Required Story Beats

Currently, users can configure probabilities and reroll seeds until they like the result. A powerful addition would be constraint-based generation: users specify certain required facts, and the generator builds around them while preserving deterministic behavior.

Examples of constraints:

- At least one warzone within two jumps of the subsector capital.
- Exactly one forge world in Subsector A.
- A named faction must have hidden presence on at least three worlds.
- The sector must contain a disconnected or perilous frontier cluster.
- A shrine world must be contested by Ecclesiarchy and Chaos factions.
- A Rogue Trader faction must control at least one trade route.
- There must be a safe route between two named systems.
- No more than 20% of systems may be uncharted.

A constraint file might look like:

```toml
[[constraints]]
id = "nearby-warzone"
type = "minimum_systems_matching"
count = 1
within_hops_of = "capital_system"
max_hops = 2
where.system_state = "Warzone"

[[constraints]]
id = "cult-subplot"
type = "faction_presence_count"
faction = "fac-ash-brood"
minimum = 3
presence = "Hidden"
```

The implementation should avoid non-deterministic search. A straightforward approach is deterministic seed scanning: given a base seed, derive candidate sub-seeds in a stable order, generate summaries, and pick the first candidate satisfying constraints. The manifest should record the base seed, selected candidate index, and constraint digest.

For performance, a summary-only prepass could evaluate constraints before full export. If no candidate satisfies the constraints within a configured limit, the tool should return a helpful report showing which constraints failed most often.

The GUI could offer a constraint builder with validation and a "find matching sector" workflow. The CLI could provide:

```bash
sectorforge generate --constraints constraints.toml --max-candidates 500
```

Why this matters: rerolling is fun, but campaign authors often need specific premises. Constraint-based generation lets users request a sector that supports their story without manually editing everything afterward.

## 16. Provenance, Explainability, and "Why Did This Happen?" Inspector

The current generator is deterministic and validates output, but users may still ask why a faction appeared on a world, why a route exists, or why a system became a warzone. An explainability inspector would make procedural results easier to trust and tune.

This feature would record optional provenance traces during generation. A trace should not store every RNG call by default, because that could bloat output. Instead, it can be generated on demand or stored in a separate debug artifact.

Useful explainability queries:

- Why did this world type get selected?
- Which candidate weights contributed to this world?
- Why is this faction present here?
- Which preferences multiplied its odds?
- Why is this route hazardous or absent?
- Why is this system classified as `Warzone`?
- Why is this faction the economic hegemon but not sovereign?
- Why did this subsector choose this capital?
- Why is this crisis forecast high risk?

A CLI command could look like:

```bash
sectorforge explain \
  --sector out/sector.json \
  --entity sys-0014-w02 \
  --question faction-presence \
  --faction fac-ash-brood
```

The output should be concise but explicit:

```markdown
## Explanation: faction presence on sys-0014-w02

Faction: Ash Brood
World: Karthax II

Contributing factors:
- Base faction weight: 1.20
- Preferred world type matched: MiningWorld × 1.50
- Preferred notable feature matched: Underhive × 1.30
- Covert disposition bonus: × 1.20
- Existing instability: +12 hidden influence
- Final candidate weight rank: 2 of 17
```

The GUI could add a "Why?" button next to generated fields. This would be especially valuable in the data editor: after changing a faction preference or route modifier, users could see how the change affected generation.

Why this matters: procedural tools are easier to use when their outputs are inspectable. Explainability helps users tune data files rather than treating the generator as a black box.

## 17. Batch Sector Atlas and Multi-Sector Generation

The current scope is a single sector, with a `generate-system` command for isolated systems. A natural expansion is a batch atlas mode that generates multiple sectors as adjacent or related regions while keeping each sector independently usable.

This feature should not require simulating an entire galaxy. Instead, it should generate a `SectorAtlas`: a collection of sector projects or outputs, each with its own seed, grid, manifest, and exports, plus cross-sector metadata.

Atlas features could include:

- Sector-level coordinates in a larger map.
- Cross-sector warp routes.
- Shared factions with per-sector power summaries.
- Segmentum or region-level political summaries.
- Cross-sector campaign fronts, such as crusades, hive fleet tendrils, or refugee flows.
- Batch manifests that include the digest of every sector manifest.

Example atlas config:

```toml
[atlas]
id = "calixis-border-atlas"
width = 3
height = 2
base_seed = "hadrumetum-2026"
sector_template = "examples/m42_project"

[atlas.cross_sector_routes]
density = 0.15
max_distance = 2
```

The generator could derive each sector seed from `blake3("sectorforge:atlas:{base_seed}:{sector_coord}")`, preserving the existing deterministic model. Cross-sector routes would be generated after individual sectors exist.

The GUI could provide an atlas overview map where clicking a sector opens the normal sector view. CLI batch exports could create one folder per sector plus an atlas-level Markdown summary.

Why this matters: some campaigns outgrow one sector, and writers may want neighboring regions for context. Atlas mode provides scale without bloating the core sector schema.

## 18. Automated Balance and Interestingness Reports (DONE)

Users currently reroll until a sector "feels interesting." The application can help by scoring generated sectors for balance and narrative density.

An `interestingness` report would compute metrics such as:

- Faction dominance concentration.
- Number and distribution of contested worlds.
- Route graph choke points.
- Distance from safe core to dangerous frontier.
- Diversity of world types.
- Presence of asymmetric control: legal ruler differs from hidden master or economic hegemon.
- Number of high-value worlds under threat.
- Subsector political diversity.
- Travel risk between major hubs.
- Count of mission-worthy flashpoints.

The tool could output a scorecard:

```markdown
# Sector Interestingness Report

Overall: 84 / 100

Strengths:
- Strong frontier/core contrast.
- Three major factions have overlapping but distinct power bases.
- Two route choke points connect high-value subsectors.
- Six worlds have mismatched sovereignty and hidden control.

Weaknesses:
- Too few xenos presences for the configured faction roster.
- Subsector C has low route connectivity and few hooks.
```

This should be configurable. Some users want balanced sandbox play; others want bleak imperial collapse, a dominant villain, or a trade-heavy campaign. Profiles could define desired ranges:

```toml
[interestingness_profiles.political_sandbox]
contested_worlds = { min = 5, max = 15, weight = 1.0 }
faction_concentration = { target = 0.45, weight = 0.8 }
route_chokepoints = { min = 2, weight = 0.6 }
```

This pairs naturally with constraint-based generation. The CLI could scan multiple deterministic candidate seeds and rank them by interestingness, letting the user choose from the top results.

Why this matters: procedural generation produces many valid outputs. Interestingness scoring helps users find the outputs best suited to their intended campaign tone.

## 19. Validation Rule Authoring and Custom Invariant Plugins

The application already has strong validation, but users with custom settings may want custom rules. For example, a non-40k reskin might require every inhabited world to have a trade code, or a campaign setting might forbid certain faction/world combinations.

A custom validation rule system would let project authors define additional checks in TOML without changing Rust code.

Example rules:

```toml
[[validation.rules]]
id = "no-chaos-on-paradise-worlds"
severity = "error"
entity = "world"
when.world_type = "ParadiseWorld"
forbid.faction_kind = "chaos"
message = "Paradise worlds in this setting cannot start with Chaos presence."

[[validation.rules]]
id = "forge-world-needs-industry"
severity = "warning"
entity = "world"
when.world_type = "ForgeWorld"
require.minimum_power.industrial = 60
```

The first implementation should support a limited declarative expression language: equality, membership, numeric comparison, existence, count, and references to faction kind or world tags. Avoid arbitrary scripting at first, because scripting complicates determinism, sandboxing, and portability.

The GUI data editor could show custom validation warnings live. The CLI could include custom rule results in the existing validation report. The manifest should record the digest of validation rule files.

Why this matters: the overview emphasizes that the data layer is setting-agnostic. Custom validation lets users enforce the assumptions of their own setting rather than only the built-in assumptions.

## 20. In-Application Changelog and Campaign Session Log

The proposed `SectorSave` split can store runtime state, but users also need a human-readable record of what happened during play. A campaign session log would connect generated sector state to actual table history.

This feature would add a `CampaignLog` structure, probably stored inside or alongside `SectorSave`. It would contain dated entries, affected entities, tags, and optional mechanical changes applied to the sector.

Example entry:

```json
{
  "id": "log-0018",
  "session": 7,
  "title": "The Fall of Veyr Station",
  "date": "campaign:143.817.M41",
  "entities": ["sys-0012", "route-sys-0012-sys-0008", "fac-ash-brood"],
  "summary": "The players exposed the station-master as a cult collaborator, but failed to prevent the fuel depot detonation.",
  "state_changes": [
    { "entity": "sys-0012", "field": "stability.public_order", "delta": -8 },
    { "entity": "route-sys-0012-sys-0008", "field": "hazard", "set": "Hazardous" }
  ]
}
```

The GUI could offer a session log editor with entity autocompletion. When viewing a system, world, route, faction, NPC, or mission, the user could see related log entries. Markdown export could include a chronological campaign appendix.

This feature should distinguish generated chronicle history from played campaign history. The generated history explains the setting before play; the campaign log records what the table changed.

Why this matters: once users begin playing in a generated sector, they need continuity tools. A session log helps the sector remain a living campaign document rather than a one-time export.

## 21. Recommended Implementation Order

The features above are intentionally modular, but some depend on others. A practical implementation order would be:

1. **Scenario diffing and explainability** — these improve development and user trust immediately.
2. **Briefing profiles** — this builds directly on existing intel and export systems.
3. **Mission seeds** — high user value, mostly derived from existing state.
4. **Campaign fronts** — builds on mission seeds, conflict, stability, and faction relations.
5. **Faction relation matrix** — strengthens politics and supports fronts.
6. **Historical chronicle** — benefits from relations, claims, and fronts.
7. **NPCs and offices** — adds human-scale detail once political structures are stable.
8. **Planetary sites** — gives missions and NPCs concrete locations.
9. **Resource/tithe model** — adds strategic causality and supply-chain stories.
10. **Crisis forecasting** — becomes much stronger after resources, relations, and fronts exist.
11. **Themeable maps and export adapters** — make the richer data easier to consume.
12. **Schema migration** — should begin early, but becomes mandatory before many serialized features ship.
13. **Mod packs and custom validation** — ideal once the data model stabilizes.
14. **Constraint generation and interestingness reports** — excellent advanced workflow tools after enough metrics exist.
15. **Atlas mode** — powerful, but best saved until single-sector features are mature.
16. **Campaign session log** — can be introduced any time after `SectorSave` is stable.

A smaller first milestone could include only four features: briefing profiles, mission seeds, scenario diffing, and explainability. Together, they would make the existing application much easier to use without requiring a large new simulation model.

## 22. Design Principles for All New Features

Every new feature should follow the same principles that make the current application strong.

First, generation should remain deterministic. New stages should derive their randomness from independent stage keys, so adding a chronicle generator does not reshuffle worlds or routes.

Second, data should remain inspectable and editable. If a feature introduces new weights, templates, names, or rules, they should live in project files rather than hidden code whenever possible.

Third, generated state and campaign state should stay separate. Generated facts belong in `sector.json`; user edits, session outcomes, completed missions, changed NPC status, and evolved fronts belong in `SectorSave` or related save files.

Fourth, exports should remain consistent. If redaction hides something, it should hide it across Markdown, JSON, CSV, PNG, and adapters. If a map theme changes presentation, it should not change data.

Fifth, every derived conclusion should be explainable. Users should be able to inspect why a route exists, why a faction is present, why a crisis is forecast, or why a mission seed was suggested.

Finally, the application should remain a setting generator rather than a game engine. These features should support play, writing, and campaign preparation without introducing mandatory turns, victory conditions, player ownership, or tactical combat rules.
